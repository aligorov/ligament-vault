# Аудит отказоустойчивости Ligament Vault — 28 ноября 2026

Объект проверки — ревизия `2380e03a9ae14e7a1e001c278d81ea1aa4ff015c`. Целевые требования — доступ к файлам через DNS при отказе узлов, восстановление избыточности, внешнее S3, журнал действий клиентов и конфигурация только в БД.

[Измерения по сценариям и контрольные хеши в JSON](2026-11-28-ha-evidence.json)

**Пять узлов выдержали все десять парных отказов в сквозном FTPS-тесте.** Для этого использовались пять голосующих участников и три копии данных. Измеренный интервал восстановления составил 0,98–88,07 с при управляемом переключении локального DNS. В штатной автоматике обнаружены блокирующие дефекты переключения и ремонта.

**Вердикт для штатных трёх узлов.** При потере двух голосующих участников etcd теряет большинство, а размещение SeaweedFS `100` оставляет по две копии тома. Потеря двух держателей сделала ранее подтверждённый файл недоступным. Зелёный статус контейнера, наличие копии в бакете и успешное избрание нового PostgreSQL primary по отдельности недостаточны для приёмки файлового сервиса.

## Метод и границы

Испытания выполнены на одном хосте Docker Desktop 29.9.3 / ARM64, в отдельных приватных сетях с тестовыми DNS-именами, одноразовыми ключами и данными. Узлы моделировались отдельными процессами и контейнерами, для испытания всей ноды одновременно завершались её процессы. ЦОД моделировались отдельными метками размещения. Потеря хоста Docker, WAN-задержки, кэши публичных рекурсивных DNS и внешние облачные аккаунты в измерения не входили. По выбору владельца использован локальный стенд.

В тестах фиксировались успешные ответы клиенту, содержимое до и после отказа и SHA-256. Различаются ответы на запись, последующее чтение полного файла и наличие байтов на физическом томе. Каждая приведённая длительность — отдельное наблюдение, включая ожидание следующей клиентской пробы. Из этих наблюдений нельзя получить процентиль доступности или верхнюю границу RTO/RPO. Для PostgreSQL, томов и клиентского протокола время измерялось независимо.

Для повторения матрицы на изолированной сети сначала подтвердить исходный файл и число его копий, затем сохранить список действующих лидеров. Для каждой пары выключить её процессы, направить то же клиентское имя на уцелевший edge, прочитать старый объект и выполнить новую загрузку с контрольным скачиванием. Перед следующим случаем вернуть узлы, проверить роли, потоковую репликацию, размещение и все уже принятые файлы. Контроль FTPS использовал 131 072 детерминированных байта на файл.

Все три задания CI по этой ревизии успешны. В существующей интеграционной проверке файл, переданный по SFTP на один узел, скачивается с двух других по IP. Здесь дополнительно проверены неизменное DNS-имя и аварийные сценарии. При локальном синтаксическом проходе ошибок в 26 shell-файлах и Python-панели не обнаружено. ## Сквозная проверка трёх нод

На каждой логической ноде остановлены вместе etcd, Patroni/PostgreSQL, SeaweedFS (Master, Volume, Filer, S3) и SFTPGo. Файловый клиент использовал explicit FTPS, контрольный объект 128 КиБ, TLS с проверкой имени, отдельные соединения и прежний FQDN. Метаданные Filer и SFTPGo хранились в PostgreSQL через HAProxy. Применялись проектные шаблоны PostgreSQL/HAProxy/Filer/S3/SFTPGo с адаптацией адресов к изолированной сети. Параметры Patroni оставлены штатными, включая TTL 75 с. Тестовый пользователь был загружен в БД, автоматическое создание администратора из ENV отключено. Лабораторный DNS переключался вручную, узлы имели раздельные диски. Между строками таблицы стенд создавался заново.

| Первый отказ → второй до возврата первого | Одна нода, от отключения до проверенного чтения / завершения последующей записи с чтением | После потери пары | Возврат исходных нод |
|---|---|---|---|
| 1 → 2, при первом отказе потерян PG primary | ≈85,71 с / ≈86,07 с | Исходный файл читался на ранних пробах. К 87-й секунде чтение прекратилось. Все три пробы записи без подтверждения. | Хеши исходного и записанного после первого отказа файлов совпали, новая запись прошла. |
| 2 → 3, PG primary оставался на 1 | ≈0,46 с / ≈0,83 с | Чтение и запись без успеха на всех трёх пробах до 87-й секунды. | Оба файла прочитаны с правильными хешами, новая запись прошла. |
| 3 → 1, PG primary оставался на 2 | ≈0,38 с / ≈8,61 с | Старый файл читался на первых двух пробах. К 87-й секунде чтение прекратилось. Новая запись не подтверждалась. | Оба файла прочитаны с правильными хешами, новая запись прошла. |

Во всех девяти попытках записи после потери двух нод клиент не смог закончить цикл загрузки и контрольного скачивания. Отдельная SQL-проверка показала, что после потери обеих реплик прежний primary ещё принимал записи на 3-й и 25-й секундах. На 53-й и 90-й секундах подтверждения уже не было. Если отключался сам primary вместе с одной репликой, подтверждений не было на всех четырёх пробах обеих пар. После возврата участников снова было две streaming-реплики, ранее сверенные маркеры присутствовали. Это различие важно для клиента, которому нужно подтвердить сохранность файла целиком.

Отдельный прогон с динамическими IP выявил ещё один режим отказа. После последовательных отключений и возвратов Patroni избрал primary, однако подтверждения через HAProxy не было за 155 с. Независимый опыт со сменой адреса ниже воспроизводит устаревший маршрут. В матрице с возвратом пары SQL-проверки перезапускали тестовый HAProxy после изменения адресов. Два последних трёхузловых файловых прогона использовали закреплённые внутренние адреса и DNS-имена.

### Потеря подтверждённой SQL-записи

Отдельный опыт с PostgreSQL 16.16 и Patroni 3.3.11 воспроизводит риск асинхронной репликации. До испытания один контрольный маркер находился на всех трёх узлах. Две PG-реплики остановлены, все три участника etcd продолжали работать. Прежний primary зафиксировал новый маркер и вернул подтверждение клиенту; отдельное SQL-соединение повторно прочитало значение. Затем этот primary аварийно отключили, а две отставшие реплики запустили. На новом primary контрольная строка сохранилась, число строк с подтверждённым поздним маркером оказалось равным нулю. Нулевой RPO для такого порядка отказов опровергнут наблюдением. Это специально созданное окно отставания, его частота в эксплуатации не измерялась.

## Клиентские протоколы и DNS

В изолированной зоне `files.vault.test` (TTL 2 с) клиент до отказа и после перехода на второй SFTPGo 2.7.6 выполнил загрузку и скачивание 262 144 байт по SFTP, explicit FTPS в режиме PASV и через настоящую форму HTTPS WebClient. Все хеши совпали. SFTP-клиент проверял закреплённый ключ сервера, FTPS защищал канал данных, WebClient использовал cookie и CSRF. На втором узле клиент повторно прочитал все три старых файла и записал новые.

Активный edge завершён аварийно. При старой записи SFTP-клиент получил таймаут. Лабораторная DNS-запись изменена вручную через 9,120 с, первое проверенное чтение через прежнее имя завершилось через 11,411 с от отключения. Этот тест использовал два edge, PostgreSQL и общий локальный том. Он измеряет переподключение клиента при смене A-записи. Автоматическое решение арбитра проверено отдельно.

| Дефект | Доказательство |
|---|---|
| Арбитр сохраняет успешное переключение при отказе DNS | Два прохода штатной логики демона с локальным DNS-hook. При возврате ошибки реальная тестовая запись осталась на прежнем адресе, но `active_ip` и время переключения обновились, счётчик отказов обнулился, инициирована публикация lease. Во втором проходе обновление DNS не повторилось. Контроль с успешным hook изменил и запись, и состояние. При отдельном локальном ответе HTTP 503 сохранение ошибочного состояния пережило перезапуск арбитра. После восстановления DNS API следующий цикл запрос не повторил. |
| Негодный SFTP endpoint проходит пробу | Настоящая TLS-страница входа вернула 200. Тестовый TCP-сервис на порту SFTP закрывал соединение без SSH-баннера. Штатная проба вернула 0. После закрытия порта вернула 1. |
| Смена IP действующего DNS-имени оставляет HAProxy со старым адресом | HAProxy 3.0.31 проверен со штатным генератором и тестовыми backend. После смены A-записи с TTL 2 с прямой клиент получал новый TCP-маркер и HTTP 200 от `/primary`. Через HAProxy маршрута не было на 5-й, 10-й и 15-й секундах как при числовом IP, так и при имени без `resolvers`. Явный reload восстановил маршрут с FQDN; для числового адреса потребовались изменение конфигурации и reload. Штатный `docker compose up -d --no-deps` после изменения содержимого файла сохранил прежний процесс и старый маршрут. |
| Требование DNS для нод не выполнено | Валидатор принял публичный домен и узел с IPv4. Эквивалентный адрес узла в виде FQDN отклонён с `AddressValueError`. Код подключения VPS требует IPv4, а шаблоны формируют peer URL и сетевые правила из IP. |
| Запуск только с БД не поддержан | В чистом каталоге конфигурации `clusterctl --dry-run status` вернул код 1 с требованием `cluster.env`. Панель читает и записывает файловую конфигурацию, передаёт S3-секрет дочернему процессу через окружение. При холодном запуске SFTPGo с исходным `create_default_admin` и пустой БД образ также потребовал переменные начального администратора. |

Изолированный отказ одного FTPS-протокола также прошёл мимо автоматики. Работали HTTPS и настоящий SFTP с аутентифицированной загрузкой, FTPS не принимал соединение. Три вызова штатной логики сохранили прежний адрес и нулевой счётчик ошибок. Для обратного переключения действуют 3 600 с ожидания и пять проб с четырьмя интервалами по 30 с. Минимум 3 720 с отсчитывается от предшествующего переключения и описывает возврат на предпочтительный узел. В отдельном тесте функций сравнение двух отсутствующих значений LSN пропустило реплику через соответствующую проверку; остальные ворота проверялись отдельными сигналами. Фоновый ремонт томов по конфигурации выполняется с паузой 17 минут, а штатный chaos-тест после отключения admin ждёт 3 с и проверяет наличие команды в конфигурации. Автономный ремонт с ожиданием полного фонового цикла в этом аудите не измерен. ## Диагностика потери узла

Штатная `check_node_health` получила от тестового SSH-транспорта код 255 без stdout. Поля Patroni, Volume, Filer, HAProxy и SFTPGo для этой ноды оказались пустыми. Вклад узла в число ошибок и предупреждений — **0 и 0**. Функция проверяет строки `DOWN` и `ERR`, а ошибка SSH подавляется до разбора ответа. Из-за этого потерянный хост сам по себе не делает итоговый статус критическим; другие проверки могут независимо поменять результат. ## Журнал клиентских действий

SFTPGo создал реальные JSON-события Upload/Download для SFTP, FTP и HTTP. В них были время, пользователь, адрес клиента, протокол, виртуальный путь, размер, длительность и идентификатор соединения. На резервном edge сопоставлены 3 загрузки и 7 скачиваний с выполненными клиентскими действиями. Проект по умолчанию задаёт локальный Docker `json-file` с ротацией 3 × 50 МБ. Лог задач панели хранится в памяти; создание пользователя может вывести сгенерированный пароль. В отдельной проверке настоящие Upload/Download с уникальным именем файла и идентификаторами соединений найдены в журнале контейнера. Полный дамп данных тестового PostgreSQL (23 публичные таблицы и записи трёх клиентов) не содержал ни этого имени, ни этих идентификаторов до и после удаления SFTPGo. После удаления `docker logs` вернул код 1. История этих операций в проверенных хранилищах утрачена.

В раздельном прогоне пяти успешным входам соответствовали пять записей `login` уровня INFO. Одна попытка клиента с неверным паролем дала две записи `connection_failed` уровня DEBUG для разных методов SSH-аутентификации. Переименованию соответствовала одна запись Rename с обоими путями, удалению — одна Remove и ответ 404 при прямом чтении ключа. При прерванной загрузке сервер оставил Upload уровня INFO с 1 572 864 байтами без признака ошибки. Клиент получил таймаут, полный размер составлял 16 МиБ. Такой журнал сам по себе не подтверждает завершение передачи со стороны клиента.

## Приоритет исправлений и повторная приёмка

1. **Сохранность данных.** Устранить публикацию усечённого файла под конечным именем либо сделать такое состояние однозначно различимым для потребителя. Сделать восстановление старых файлов на чистые диски проверяемым до объявления успеха. В едином тесте проверить байты, время восстановления, права и WORM. Закрыть ветку повторного bootstrap, способную стереть существующие данные при потере локального состояния.
2. **Возврат избыточности.** Исправить присоединение learner, обработку ID и блокировку ремонта томов. Повторить с новой VPS, потерянным диском и обрывом операции посередине. Проверять реальные голоса, число копий и старые файлы с новой ноды.
3. **Доступность через DNS.** Согласовывать состояние арбитра с ответом провайдера, повторять временные ошибки, проверять реальную клиентскую операцию перед переключением. Принять FQDN в инвентаре и обеспечить переподключение peer-сервисов после изменения адреса.
4. **Конфигурация и аудит в БД.** Закрыть зависимости панели, CLI, арбитра и фоновых заданий от ENV. Проверить холодный старт и восстановление источника конфигурации. Доказать сохранность событий по квитанциям до потери узла, отсутствие пропусков/дублей и секретов при ротации и недоступности БД.
5. **Приёмка двух отказов после исправлений.** Повторить сквозные испытания со штатным автоматическим арбитром на целевой схеме с пятью голосующими участниками и минимум тремя копиями старых и новых томов. Для каждой пары проверять по неизменному имени вход, чтение, запись и восстановление избыточности. Условие нулевого RPO для PostgreSQL требует отдельного решения о режиме репликации.
