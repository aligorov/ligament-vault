# Ligament Vault — Отказоустойчивый гео-кластер SFTP / FTPS / Web / WORM

Готовый файловый кластер корпоративного уровня на **3–5+ обычных Linux VPS в разных дата-центрах без VPN-оверлея** (`SFTPGo + SeaweedFS 4.x + Patroni/PostgreSQL 16 + etcd + mTLS`) с единой **HTTPS Веб-панелью управления (`:9443`)**, браузерным файловым клиентом (`:443`), неизменяемым **WORM-архивом (`COMPLIANCE`)** и интеграцией с **Ligament 2FA**.

---

## ⚡ Установка одной командой

Подключитесь по SSH (`root`) к главному серверу (**Ubuntu 22.04 / 24.04 LTS**) и выполните:

```bash
curl -fsSL https://raw.githubusercontent.com/aligorov/ligament-vault/main/install.sh | sudo bash
```

Установщик выполняет три шага.

1. Установит Docker, Compose, `age` и все системные утилиты.
2. Сгенерирует все криптостойкие пароли, JWT и ключи шифрования автоматически (никаких ручных конфигов).
3. Запустит **HTTPS Веб-панель управления на порту `9443`** и выведет адрес и команду получения пароля.

Дальше откройте `https://<имя-контроллера>:9443` в браузере:
- **Подключите остальные чистые VPS прямо по SSH из браузера** (укажите DNS-имя, порт и разовый `root`-пароль от хостера — панель сама зайдет на сервер, пропишет SSH-ключ, установит Docker и подготовит диск).
- Нажмите одну кнопку **«🚀 Объединить в кластер и установить всё»** — все серверы автоматически свяжутся по mTLS и соберутся в единый отказоустойчивый кластер (а позже точно так же в 1 клик можно подцепить 4-й или 5-й VPS на лету!).

## 🌐 Два веб-интерфейса из коробки

| Интерфейс | Адрес | Для кого и зачем |
| :--- | :--- | :--- |
| **Панель управления кластером (`Ligament Vault UI`)** | `https://<IP_или_ДОМЕН>:9443` | **Администратор:** установка кластера в 1 клик, живой мониторинг нод/ДЦ/БД/дисков, создание клиентов (`/work` + `/worm`), квоты, настройка `Ligament 2FA`, бэкапы, добавление нод, живая консоль задач |
| **Файловый веб-клиент (`WebClient`)** | `https://<ДОМЕН>:443` | **Пользователи:** загрузка, скачивание и просмотр папок `/work` и `/worm` прямо в браузере (TLS 1.3 + поддержка 2FA) |

Помимо браузера, пользователи подключаются по **SFTP (`порт 2022`)** и **FTPS Explicit (`порт 21`, PASV `50000–50199`)**.

## 🛡 Ключевые возможности

- **Гео-распределение без VPN:** прямое соединение между ДЦ по сквозному **mTLS (ECDSA P-256)** с Zero-Knowledge Remote-CSR (приватные ключи никогда не покидают серверы) и 4 JWT-ключами SeaweedFS.
- **Два типа хранилища у каждого клиента:**
  - `/work` — рабочий каталог с версионированием и докачкой оборванных загрузок.
  - `/worm` — неизменяемый архив (`S3 Object Lock COMPLIANCE`): защищённую версию объекта нельзя удалить до истечения срока хранения.
- Арбитр проверяет HTTPS, SFTP и пассивный FTPS. После подтверждения смены адреса провайдером он сохраняет состояние в своей SQLite. Время переключения со стороны клиента зависит от интервала проб, восстановления сервисов, кэширования DNS и повторного подключения клиента.
- Панель, CLI и фоновые задачи используют базу контроллера `control.sqlite3`. Пароли, ключи и токены зашифрованы с помощью age. Сервисы получают конфигурационные файлы своего формата при рендеринге.
- **Полная автономность образов:** предсобранный образ PostgreSQL 16 + Patroni + pgBackRest публикуется в `aligorov/ligament_vault_patroni:16` (`ghcr.io/aligorov/ligament_vault_patroni:16`) с автоматическим локальным fallback из [Dockerfile.patroni](Dockerfile.patroni).

## 💻 Управление из терминала (`ligactl`) — опционально

Все действия доступны в веб-панели `:9443`, но при необходимости установлена глобальная команда `ligactl`:

```bash
ligactl config get PANEL_ADMIN_PASSWORD                           # Получить пароль панели в доверенном терминале
ligactl status --strict                                           # Состояние всех узлов, БД, SeaweedFS и SSL
ligactl user add --username bank1 --quota-gb 100 --generate-password  # Создать клиента (/work + /worm)
ligactl scale add --ip n4.storage.example --dc dc4 --role quorum                      # Добавить 4-й узел в кластер
ligactl dr restore --latest                                       # Восстановить весь кластер из S3 бэкапа
ligactl publish-image                                             # Собрать и запушить образ Patroni в Docker Hub
```

Архитектурная спецификация: [PLAN.md](PLAN.md) · Готовый дашборд Grafana: [ligament-vault-dashboard.json](configs/grafana/ligament-vault-dashboard.json).

## База управления и DNS

На контроллере нужны Python 3, `age`, `age-keygen` и `htpasswd` из пакета `apache2-utils`. При обновлении выполните `./ligactl config init` в существующем каталоге управления. При первом запуске команда импортирует старые `cluster.env`, `versions.env` и секреты. Для прежнего нестандартного ключа доступен параметр `--legacy-identity /путь/к/ключу`. Последующие чтения и изменения выполняются через БД. После сверки перенесите оставшиеся старые файлы в защищённый архив. Для восстановления контроллера сохраните согласованную копию SQLite, отдельно файл `.control.agekey`, PKI, общие SSH host keys и прежний ключ age для ранее зашифрованного CA. Для копии открытой БД используйте SQLite Backup API.

У каждой ноды должно быть своё имя с одной A-записью. Имена нод и арбитра должны разрешаться с контроллера и всех участников кластера. Клиенты используют общее имя `DOMAIN`, указанное в TLS-сертификате. При изменении адреса ноды обновите DNS и выполните `sync-config` для привязок сетевых сервисов, UFW и `pg_hba`. Для автоматического переключения укажите в БД адрес внешнего арбитра и настройте DNS-провайдер. Пользовательский DNS-hook устанавливается на арбитре по пути из БД.

Пример начальной настройки для пяти независимых площадок, до первого `install`:

```bash
./ligactl config init
printf '%s' 'n1.storage.example:dc1:node1 n2.storage.example:dc2:node2 n3.storage.example:dc3:node3 n4.storage.example:dc4:node4 n5.storage.example:dc5:node5' | ./ligactl config set CLUSTER_NODES
printf '%s' 'files.storage.example' | ./ligactl config set DOMAIN
printf '%s' 'arbiter.storage.example' | ./ligactl config set ARBITER_IP
./ligactl config ha-five
./ligactl preflight
```

`ha-five` задаёт пять голосующих узлов, политику SeaweedFS `200` (три копии в разных ЦОД) и целевое число синхронных реплик PostgreSQL 2. При трёх голосующих узлах запись требует большинства из двух. При пяти нужны три. Строгий режим Patroni блокирует подтверждение записи при отсутствии синхронных реплик. При нехватке кандидатов Patroni может уменьшить их фактическое количество до одного. `ligactl status --strict` сверяет фактическое состояние с целью. Для действующего кластера используйте `scale add` и `scale replace`; смена значения репликации по умолчанию затрагивает новые тома. После аварийного завершения операции контроллера перед `unlock --force` убедитесь, что исходный процесс завершён.

## Локальный стенд

`./ligactl lab up --with-arbiter --dns-zone lab.test` создаёт три Ubuntu VM и отдельную VM арбитра. Добавьте выведенные A-записи в частный DNS, доступный контроллеру и гостям, и повторите команду. Она проверит каждое имя из всех VM и сохранит FQDN в БД lab. По умолчанию клиентский адрес — `files.lab.test`. Для локального тестового сертификата доверенный файл находится в `environments/lab/.ssl/certificates/files.lab.test.crt`. Без `--dns-zone` инвентарь использует адреса IPv4.

Для теста внешнего S3 подготовьте отдельный бакет и укажите его HTTPS endpoint, регион, бакет и ключи в `BACKUP_S3_*` базы lab. Сертификату endpoint должны доверять клиенты резервного копирования. `./ligactl lab verify --with-backup` запускает установку, проверку S3/WORM кластера, запись полного бэкапа во внешний бакет и проверку восстановления.

## Аудит клиентов и восстановление

События входа, отказа входа и файловых операций SFTPGo собираются на каждой ноде. Сборщик сохраняет очередь в SQLite под `<SFTPGO_DATA_DIR>-audit/spool`, передаёт её в PostgreSQL через локальный HAProxy и удаляет из очереди подтверждённые записи. Повторная отправка защищена уникальным идентификатором. При утрате диска до отправки теряются его неподтверждённые события. Запрос выполняется в базе `postgres` под ролью с правом чтения.

```sql
SELECT received_at, node, event->>'username' AS client,
       event->>'sender' AS operation, event->>'virtual_path' AS path,
       event->>'failed' AS failed
FROM public.client_events
ORDER BY received_at DESC
LIMIT 50;
```

Для внешней папки задайте HTTPS endpoint с DNS-именем, регион и бакет через панель или `ligactl user add-s3-folder`. CLI принимает секрет через stdin с флагом `--secret-key-stdin`. Для проверяемой публикации в рабочую или внешнюю папку доступен клиент с загрузкой во временное имя и проверкой SHA-256:

```bash
python3 scripts/ops/publish-sftp.py -P 2022 -i ~/.ssh/client client@files.storage.example ./report.bin /work/report.bin
```

Для этого клиента нужна доверенная запись SSH host key. При прерывании прямой загрузки по SFTP клиент без ожидаемого размера может оставить укороченный файл. В `/worm` переименование ограничено политикой архива.

Внешний бакет для DR задаётся отдельно параметрами `BACKUP_S3_*` в БД. `ligactl backup full` создаёт точку восстановления PostgreSQL и физических томов. `ligactl dr verify-backup` проверяет целостность и запускает пробное восстановление PostgreSQL. Для `dr restore --target-time` укажите точное время опубликованной совместной точки UTC. Сохраните ключ шифрования вместе с резервной копией конфигурации. Старые резервные копии с одними метаданными Filer не подходят для восстановления файлов на пустых дисках.

При создании совместного снимка должны отвечать все настроенные узлы томов. Если за время проверки изменились исходные тома, задание повторяет попытку до трёх раз. Статус ошибки сохраняет последнюю завершённую точку. Данные клиентских папок, подключённых к независимому S3, резервирует владелец соответствующего бакета.


## Локальная проверка переключения DNS

Из корня репозитория запустите `python3 tests/integration/dns_failover.py`. Нужны Docker, Python 3, OpenSSL и ssh-keygen. Стенд поднимает собственную DNS-зону и два SFTPGo, останавливает активный узел, дожидается обновления A-записи арбитром и сверяет содержимое файла по FTPS.

## Повышение репликации действующего кластера

Для перехода с `100` на `200` сначала добавьте оба голосующих узла при действующей политике и проверьте резервную копию. В согласованное окно приостановите запись и убедитесь, что доступны три независимых ЦОД с достаточным свободным местом. Задайте в базе `SWFS_DEFAULT_REPLICATION=200`, `SWFS_VOLUME_GROWTH_COUNT=3` и `PG_SYNC_STANDBY_COUNT=2` через `ligactl config set`. Выполните `ligactl sync-config`. Для явной настройки синхронности эта команда применяет параметры через Patroni DCS и проверяет число синхронных реплик на primary. Затем обновите сервис `swfs-master` по одному на голосующих нодах командой `docker compose up -d --no-deps swfs-master` из каталога стека. Проверяйте восстановление кворума перед переходом к следующей ноде.

В `weed shell`, подключённом к действующим master и filer, выполните следующие команды. Шаблон `*` выбирает все коллекции. Для разных политик укажите конкретную коллекцию.

```text
lock
fs.configure -locationPrefix=/ -volumeGrowthCount=3 -replication=200 -apply
volume.configure.replication -collectionPattern=* -replication=200
unlock
```

После регистрации новых настроек томов на master выполните `lock`, `volume.fix.replication -apply`, `unlock` в одной сессии. Перед возобновлением записи дождитесь успешного `ligactl status --strict` и сравните SHA-256 контрольного файла через клиентский DNS.
